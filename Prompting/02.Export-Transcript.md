# MomTest 계약 발견 — Product Discovery / TDD 분석

_Exported on 2026-06-24 from Cursor_

---

## User

당신은 MomTest 방식으로 도메인 규칙을 발견하는 Product Discovery / TDD 분석 에이전트입니다.

목표는 사용자의 요구사항이나 인터뷰 메모에서 테스트 가능한 계약을 추출하는 것입니다.
계약은 반드시 ID를 가져야 하며, 이 ID는 테스트와 구현을 연결하는 "추적의 못"으로 사용됩니다.

중요 원칙:

1. 사용자의 답을 유도하지 않습니다.
2. "이렇게 하면 되나요?" 식의 확인 질문을 하지 않습니다.
3. 과거 실제 사례, 실패 경험, 경계 상황, 예외 상황을 중심으로 묻습니다.
4. 추측으로 기능을 만들지 않습니다.
5. 근거가 없는 동작은 계약 ID로 만들지 않습니다.
6. ID에 없는 동작은 구현하지 않습니다.
7. AC, 비즈니스 규칙, 예외 규칙, 불변식을 구분합니다.
8. 최종 산출물은 테스트 가능한 계약표여야 합니다.

분석 대상 요구사항:

[인터뷰 메모]
- 2024-03-12: A 3개(12,000원) + B 1개(30,000원) = 66,000원. 5만 원 넘으면 10% 할인. 기대 59,400원.
- VIP 고객은 문턱 할인 후 추가 5% 할인. 순서는 문턱 → VIP 고정.

[실제 주문 사례]
- #1107: 소계 60,000 → 결제 54,000 (10% 할인)
- #1042: 소계 48,000 → 할인 없음

[엑셀 검산]
- 66,000 × 0.9 = 59,400 (ROUND)
- VIP 추가: 59,400 × 0.95 = 56,430

[CS 클레임 / 버그]
- 수량 -1 입력 시 화면 합계 0원 표시 (기대: 오류 또는 거부)
- items 없이 제출 시 500 에러

[명시적 비범위 / 미확인]
- 쿠폰·배송비: 언급 없음
- 50,000원 정확히: "넘으면"만 확인, 50,000 포함 여부 미확인

분석 절차:

# MomTest 기반 계약 발견 분석 — 장바구니 할인 계산기

아래는 제공된 인터뷰 메모·주문 사례·CS 클레임만을 근거로 한 분석입니다. **근거 없는 동작은 계약으로 만들지 않았고**, 50,000원 경계·VIP 단독 적용 등은 OOS로 분리했습니다.

---

## Step 1. MomTest 질문 생성

유도하지 않는, 실제 사건을 끌어내는 질문입니다.

### 할인 문턱·금액 계산

1. **소계가 5만 원 근처였던 주문** 중, 직원이나 고객이 "할인이 왜 됐는지/안 됐는지" 따져본 건 어떤 주문이었나요? 그때 화면·영수증·엑셀에 각각 얼마로 찍혔나요?
2. **할인 금액이 1원이라도 어긋났던 CS 사례**가 있다면, 어떤 상품 조합이었고, 누가 어떤 식으로 다시 계산했나요?
3. **엑셀 검산과 시스템 결제액이 달랐던 적**이 있나요? 있다면 소수점·반올림이 걸린 단계가 어디였나요?

### VIP 할인

4. **VIP 고객인데 문턱 할인이 안 붙은 주문**(또는 그 반대) 때문에 연락이 온 사례가 있나요? 그때 최종 결제액은 얼마였고, 누가 어떤 순서로 할인을 적용했다고 설명했나요?
5. **VIP 할인만 기대하고 문턱 할인은 없었던 주문**이 실제로 있었나요? 있다면 소계와 최종 결제액을 기억나는 대로 말해 주세요.

### 잘못된 입력·시스템 오류

6. **수량에 이상한 값**(0, 빈칸, 문자, 소수)을 넣었을 때 실제로 화면·결제에 어떤 일이 벌어진 사례가 있나요?
7. **빈 장바구니로 제출했을 때** 고객·운영자가 본 화면이나 로그는 어땠나요? 500 에러 말고 다른 반응을 본 적이 있나요?
8. **수량 -1 입력**이 0원으로 보인 뒤, 그 주문이 실제 결제·재고·정산까지 이어졌나요, 아니면 그 전에 막혔나요?

### 규칙 조합·손실

9. **할인 규칙이 동시에 걸릴 수 있었던 주문** 중, 순서를 잘못 적용했다고 판단한 사례가 있나요? 그때 기대 금액과 실제 금액 차이는 얼마였나요?
10. **이 계산기가 틀리면 회사에 어떤 손실**이 났나요? (과다 할인, 미할인 클레임, 정산 오류 등) 가장 최근 사례를 하나 들려주세요.
11. **절대 나오면 안 된다고 생각하는 결제 결과**가 있나요? 예를 들어 할인 전보다 비싸진 금액, 음수 금액 등 — 실제로 그런 화면을 본 적이 있나요?

## Step 2. 근거 레벨 분류

| 근거 출처 | 내용 | 레벨 |
|----------|------|------|
| 인터뷰 2024-03-12 | A×3 + B×1 = 66,000 → 10% 할인 → 59,400 | L1 |
| 인터뷰 2024-03-12 | VIP: 문턱 후 추가 5% → 56,430 | L2 |
| 인터뷰 2024-03-12 | 적용 순서: 문턱 → VIP 고정 | L2 |
| 주문 #1107 | 소계 60,000 → 결제 54,000 (10%) | L1 |
| 주문 #1042 | 소계 48,000 → 할인 없음 | L1 |
| 엑셀 검산 | `× 0.9`, `× 0.95`, `ROUND` | L1/L2 |
| CS 클레임 | 수량 -1 → 화면 0원 (기대: 오류/거부) | L0 |
| CS 클레임 | items 없이 제출 → 500 에러 | L0 |
| 명시적 미확인 | 50,000원 **정확히** 포함 여부 | — (근거 부족) |
| 명시적 비범위 | 쿠폰·배송비 언급 없음 | OOS |

## Step 3–5. 계약 후보 → ID → 테스트 가능 문장

### 계약표

| ID | 계약(불변식 / 에러 / AC) | 근거 레벨 | 계층 | 테스트 아이디어 | 구현 범위 |
| -- | ----------------- | ----- | -- | -------- | ----- |
| **INV-1** | `subtotal = Σ(unit_price × qty)` (유효한 품목만) | L1 | Entity | `[{A,3,12000},{B,1,30000}]` → `66000` | `cart.py` |
| **INV-2** | `subtotal > 50000`이면 `round(subtotal × 0.9)` 반환 | L1 | Entity | `60000` → `54000`; `66000` → `59400` | `cart.py` |
| **INV-3** | `subtotal ≤ 50000`이면 문턱 할인 없이 `subtotal` 그대로 반환 | L1 | Entity | `48000` → `48000` | `cart.py` |
| **INV-4** | `is_vip=True`이면 `round(after_threshold × 0.95)` 반환 | L2 | Entity | `59400`, VIP → `56430` | `cart.py` |
| **INV-5** | `is_vip=False`이면 VIP 할인 없이 문턱 적용 후 금액 반환 | L2 | Entity | `59400`, non-VIP → `59400` | `cart.py` |
| **INV-6** | 할인 적용 순서는 항상 **문턱 → VIP** (VIP는 문턱 적용 후 금액에만 적용) | L2 | Entity | VIP+문턱 케이스에서 `66000→59400→56430` 순서 검증 | `cart.py` |
| **INV-7** | 최종 결제액은 **0 이상의 정수(원)** | L3 | Entity | 모든 AC·INV 케이스에서 `int`이고 `≥ 0` | `cart.py` |
| **INV-8** | 최종 결제액은 **항상 `subtotal` 이하** (할인으로 인상 없음) | L3 | Entity | 모든 할인 케이스에서 `final ≤ subtotal` | `cart.py` |
| **E-1** | `qty < 0`이면 인덱스를 포함한 `ValueError` 발생 (0원으로 보이지 않음) | L0 | Entity | `qty=-1` at index 0 → `ValueError`, 메시지에 index | `cart.py` |
| **E-2** | `items`가 `None`이거나 빈 리스트이면 `ValueError` 발생 | L0 | Entity | `items=None`, `items=[]` → `ValueError` | `cart.py` |
| **E-3** | 빈/누락 `items`로 HTTP 제출 시 **4xx 응답** (500 아님) | L0 | Boundary | POST with no items → status 400 (또는 422), not 500 | `app.py` |
| **E-4** | `qty < 0` 제출 시 Boundary는 오류 응답 또는 오류 메시지 표시 (합계 0원 표시 금지) | L0 | Boundary | `qty=-1` → 4xx 또는 폼 오류; body에 `0` 합계 없음 | `app.py` |
| **AC-1** | 주문 #1107: 소계 60,000 → 최종 54,000 | L1 | Entity | 통합 시나리오 테스트 1건 | `cart.py` |
| **AC-2** | 주문 #1042: 소계 48,000 → 최종 48,000 | L1 | Entity | 통합 시나리오 테스트 1건 | `cart.py` |
| **AC-3** | 인터뷰 시나리오: A×3 + B×1, non-VIP → 59,400 | L1 | Entity | 카탈로그 가격 + 수량 조합 E2E | `cart.py` |
| **AC-4** | 인터뷰 시나리오: 위 조건 + VIP → 56,430 | L2 | Entity | AC-3 + VIP 플래그 | `cart.py` |

### 테스트 가능 문장 상세 (구현 시 참조)

```
INV-1:  calculate_subtotal([{sku:"A",qty:3,price:12000},{sku:"B",qty:1,price:30000}]) == 66000
INV-2:  apply_threshold(60000) == 54000; apply_threshold(66000) == 59400
INV-3:  apply_threshold(48000) == 48000
INV-4:  apply_vip(59400, is_vip=True) == 56430
INV-5:  apply_vip(59400, is_vip=False) == 59400
INV-6:  calculate_total(items, is_vip=True) == apply_vip(apply_threshold(subtotal), True)
INV-7:  ∀ valid input: isinstance(result, int) and result >= 0
INV-8:  ∀ valid input: result <= subtotal
E-1:    calculate_subtotal([{qty:-1,...}]) raises ValueError matching index
E-2:    calculate_subtotal(None) raises ValueError; calculate_subtotal([]) raises ValueError
E-3:    client.post("/", data={}) → status_code in (400, 422)
E-4:    client.post("/", data={qty:-1}) → not 200 with total=0
```

## Step 7. 과잉 구현 방지 (OOS)

| OOS ID | 만들지 않을 동작 | 제외 이유 |
| ------ | --------- | ----- |
| **OOS-1** | 쿠폰 할인 | 인터뷰·주문 사례·CS에 언급 없음 |
| **OOS-2** | 배송비 | 명시적 비범위 |
| **OOS-3** | `subtotal == 50000`일 때 10% 할인 | "넘으면"만 확인; 정확히 5만 원 실사례·검산 없음 |
| **OOS-4** | 문턱 미달인데 VIP 5%만 적용 | VIP 예시는 문턱 적용 후(59,400)에만 근거 있음 |
| **OOS-5** | `qty == 0` 처리 규칙 | 실제 사례·클레임 없음 |
| **OOS-6** | 음수 단가(`price < 0`) | 사례 없음 |
| **OOS-7** | 비정수 수량 | 사례 없음 |
| **OOS-8** | 세금·포인트·회원 등급 확장 | 근거 없음 |
| **OOS-9** | 할인 순서 변경( VIP → 문턱 ) | 인터뷰에서 "문턱 → VIP 고정"만 확인 |
| **OOS-10** | 소수 원 미반올림 중간값 유지 | 엑셀 `ROUND`·정수 원 결제만 확인; 중간 소수 유지 사례 없음 |

## 구현 우선순위 제안 (TDD RED 순서)

1. **INV-1** + **AC-3** — 소계 계산 (66,000)
2. **INV-3** + **AC-2** — 할인 없음 (48,000)
3. **INV-2** + **AC-1** — 문턱 10% (60,000)
4. **INV-4/5/6** + **AC-4** — VIP 조합
5. **INV-7/8** — 안전 불변식
6. **E-1/E-2** (Entity) → **E-3/E-4** (Boundary)

**OOS-3**(정확히 50,000원)은 MomTest 질문 1·2번에 답이 나올 때까지 RED에 넣지 않는 것이 안전합니다.
